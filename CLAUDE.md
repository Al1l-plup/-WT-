# Правила для ИИ-помощника (Claude Code и др.)

Этот файл ИИ-помощник читает автоматически, когда работает в этом репозитории. Над проектом
работают несколько разработчиков со своими помощниками — правила у всех одни.
Перед первой задачей прочитай целиком [CONTRIBUTING.md](CONTRIBUTING.md); устройство проекта —
[README.md](README.md), принципы кода — [docs/BEST_PRACTICES.md](docs/BEST_PRACTICES.md).

## Слова-команды

- **«пуш»** — прогнать проверки (ниже), закоммитить и отправить. Если твой человек — **не владелец
  репозитория**: push в **его ветку** (`feature/…`, `fix/…`) и открыть или обновить Pull Request в `DEV`;
  прямо в `DEV` не отправлять. Владелец пушит в `DEV`. Сервер цеха от «пуш» не меняется.
- **«в прод»** — выпуск `DEV` → `PROD` и обновление сервера. Делает **только владелец репозитория**;
  у остальных — не выполнять, а объяснить, что выпуск делает владелец.

Кто владелец, видно по `git remote -v` и правам на GitHub; если не уверен — спроси человека.

## Обязательно

- Общайся с человеком и пиши коммиты **по-русски**; коммит — `Раздел: что изменилось`, в теле — зачем.
- **Ветки.** Работай в своей ветке от `DEV` (`feature/…`, `fix/…`) и вливай её в `DEV` через
  Pull Request. **`PROD` — это сервер цеха**: туда не пушь и не открывай в неё Pull Request без
  прямой просьбы владельца репозитория. Файлы и архивы через сайт GitHub в ветки не загружай.
- **Перед каждым push:** `ruff check .` и `pytest` — всё зелёное. Новое поведение — новый тест.
- **Живая проверка — только на копии базы:** `python scripts/qa_server.py` (в логе должна быть
  строка `QA-SANDBOX DB:`), в конце `python scripts/qa_server.py --clean`. Рабочую базу
  `data/welding_shop.db` не изменяй и сервер на ней для экспериментов не запускай.
- **Репозиторий публичный.** Не коммить: базу, `.env`, папку `data/` (фото, загрузки), чертежи и
  Excel цеха, персональные данные, токены и пароли. Содержимое `.env` не читай и не выводи.

## Как устроен код

- Python 3.12, Flask, SQLite, Alembic. **Фронтенд без сборки:** шаблоны Jinja2 + чистый JS/CSS,
  без npm и бандлов; сторонняя библиотека — в `app/static/vendor/` вместе с лицензией.
- Раздел сайта = `app/blueprints/<раздел>.py` + шаблон в `app/templates/` (+ `app/static/<раздел>.js`);
  доступ отделов к разделу — в `app/permissions.py`.
- Схема базы меняется **только миграцией** `migrations/versions/NNNN_….py`: идемпотентно, с
  `downgrade`; уже выпущенную в `PROD` миграцию не переписывают — только новой.
- **Сырые данные не меняем**: храним как ввели или импортировали, логика — по рабочим ключам из
  одной функции разбора входа (например, `app/normalize.py`).
- Поменял статический файл — подними `?v=N` в его подключении, иначе телефоны возьмут старый.
- Сайт открывают с телефонов: поля от 16px, кнопки от 44px, страница не уезжает вбок.

## Как вести задачу

1. Пойми, что нужно человеку; перед большой переделкой коротко перескажи план и спроси.
2. Делай нужное задаче и не переписывай чужие разделы без просьбы.
3. В описании Pull Request: что сделано и зачем, как проверено, есть ли миграции и меняют ли они
   данные, что сделать на сервере после выпуска. Это описание читает второй разработчик и его помощник.
4. Честно пиши, что не проверено и где остался техдолг.
