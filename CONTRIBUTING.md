# Как работать с проектом в Git

Короткая инструкция по совместной разработке WeldTeam MES.

## Ветки

| Ветка | Назначение |
|-------|------------|
| `DEV` | **Рабочая ветка** — сюда идут коммиты и с неё разворачивается сервер цеха. |
| `main` | Стабильная/прод-линия. Сейчас намеренно держится пустой (прод = `DEV`). |
| `feature/*`, `fix/*` | Ветки под крупную/рискованную задачу, создаются **от `DEV`** (по желанию). |

Текущая практика — один активный разработчик работает прямо в `DEV`; сервер обновляется
из `DEV` (`deploy/update.ps1`). Для крупных/рискованных изменений заводите `feature/*` от
`DEV` и вливайте обратно. В `main` без явной необходимости не коммитим.

## Типовой рабочий цикл

```bash
# 1. Обновить рабочую ветку
git checkout DEV
git pull origin DEV

# 2. (для крупной задачи) отдельная ветка от DEV
git checkout -b feature/kratkoe-opisanie      # или fix/opisanie-baga

# 3. Работать, коммитить небольшими логическими порциями
git add <файлы>
git commit -m "feat: добавил экспорт дефектов в CSV"

# 4. Запушить
git push origin DEV                            # или: git push -u origin feature/...
```

Ветку задачи после вливания в `DEV` можно удалить.

## Формат сообщений коммитов

Используем [Conventional Commits](https://www.conventionalcommits.org/):

```
<тип>: <краткое описание в повелительном наклонении>
```

Основные типы:

- `feat:` — новая функциональность
- `fix:` — исправление бага
- `refactor:` — изменение кода без изменения поведения
- `docs:` — документация
- `test:` — тесты
- `chore:` / `build:` — рутина, зависимости, структура

Примеры: `feat: планирование ТО на квартал`, `fix: неверный расчёт среднего тока`.

## Перед коммитом

```bash
pytest            # тесты должны проходить
ruff check .      # проверка стиля (по желанию)
```

Не коммитьте: `.venv/`, `.env`, `__pycache__/`, служебные файлы SQLite
(`*.db-wal`, `*.db-shm`, `*.db-journal`) — они уже в `.gitignore`.

## Изменения в схеме БД

Схема ведётся миграциями **Alembic** (`migrations/versions/`). Поменяли схему —
`alembic revision -m "…"`, опишите шаги в файле ревизии. Приложение при старте само
делает `alembic upgrade head` (`app/migrations.py`). Структуру руками в БД не правим.

Файл `data/welding_shop.db` в git **не хранится** (`.gitignore`) — репозиторий содержит
только код, миграции и справочники (`db/seed.sql`). База собирается локально
`python scripts/init_db.py`. Изменили справочные данные — пересоберите seed
(`python scripts/dump_seed.py`) и закоммитьте `db/seed.sql`, а не саму БД.
