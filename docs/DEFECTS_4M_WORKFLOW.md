# Дефекты 4M — маршрут согласования, серийность, фото, аналитика

Спецификация переделки процесса дефектов (черновик для согласования).
Статус: на подтверждении у Алибека. Пункты **[ПРЕДПОЛОЖЕНИЕ]** — требуют «да/нет».

---

## 1. Суть

Сейчас дефект закрывает фактически один отдел (WeldTeam): одно поле «причина» + одно
«решение». Делаем **последовательную цепочку согласования** между отделами (по смыслу
4M), с ранним закрытием, возвратами, серийностью, фото и статистикой времени.

4M как смысловые ярлыки этапов: **Производство ≈ Man**, **WeldTeam ≈ Machine**,
**ИТО ≈ Method/Material**.

---

## 2. Маршрут (цепочка этапов)

Дефект проходит отделы по порядку. Маршрут задаётся **по коду дефекта** и
**редактируется в Редакторе** (порядок/состав отделов можно менять).

Начальные маршруты:

| Код дефекта        | Цепочка                               |
|--------------------|---------------------------------------|
| по умолчанию (`*`) | Производство → WeldTeam → ИТО          |
| **EO**             | Производство → ИТО (WeldTeam пропущен) |
| **MN**             | Производство → ИТО (WeldTeam пропущен) |

- Регистрирует дефект **ОТК** (как сейчас). После регистрации дефект встаёт на **1-й
  этап** маршрута (Производство). ОТК — регистратор, не этап.
- **Видимость:** все отделы видят все дефекты (включая EO/MN). У каждого отдела есть
  «Входящие» = дефекты, которые сейчас на **его** этапе.

---

## 3. Действия на этапе

Действует **только отдел текущего этапа** (остальные — просмотр). Варианты:

1. **Контрмера принята → Закрыть.** Заполняет: *предполагаемая причина* + *контрмера*.
   Дефект закрывается (отдельный «вывод» не нужен — закрытие = решено).
2. **Причина не выявлена → Передать дальше.** Переходит к следующему отделу цепочки
   (поля не обязательны, можно оставить заметку).
3. **Вернуть на доработку (bounce).** Возврат **к выбранному отделу** с указанием
   причины возврата. Помечается как «возврат», влияет на статистику.
4. **Передать в ОТО (оборудование).** Любой отдел на своём этапе может передать заявку
   в **ОТО** при неисправности/несоосности оборудования (напр. несоосность клещей).
   Пока ОТО не даст контрмеру — все ждут ОТО. После контрмеры ОТО управление
   возвращается отделу-отправителю. **Если контрмера ОТО не помогла и дефект повторился
   (серия) — дефект возвращается отделу, который передавал в ОТО** (`delegated_from_dept`).

Таймстемпы входа/выхода каждого этапа пишутся → среднее время рассмотрения по отделу
(и база для «производительности отделов» позже).

### Не выявленные (конец цепочки без решения)

Если дошли до конца цепочки и причина не выявлена — дефект НЕ закрывается, переходит в
состояние **«не выявлен»**: попадает в **отдельный список** и **статистику**,
разбирается совместно на **недельном отчёте**, дальше решение принимается коллегиально.

## 4. Серийный дефект (повтор)

**Группы кодов для серии** (серия = повтор в пределах одной группы на одной точке):
- Группа **{MN}** — MN серится только с MN.
- Группа **{EO}** — EO серится только с EO.
- Группа **{остальные}** — CR, SN, LP, BN, SW, P, MI, BT, IE, MS, ME, EMU, NA, BE —
  серятся между собой в любом сочетании.

Примеры (точка №124): `BT → LP → BN` = серия (все из «остальных»);
`BT → MN` = **не** серия; `MN → MN` = серия; `EO → EO` = серия.

**Критерий:** достаточно **повторной** фиксации (2-й раз, не нужно 3). Повтор считается
серией, только если он произошёл в пределах **окна времени** (напр. ≤ 2 дней между
фиксациями). Окно **настраивается в Редакторе**. Позже окна — не серия (обычный дефект).

**Что происходит при серии:** это **переоткрытие** того же дефекта — он **возвращается
на перерассмотрение к отделу, который его в своё время закрыл**. Считается и
**возвратом** (в статистику отдела), и **серией** (в аналитику серийных). Новая фиксация
(дата, фото) добавляется как ещё одно «появление» на этом дефекте.

---

## 5. Приоритет и пометки в списке

Порядок в «Дефектах для рассмотрения» (сверху вниз):
1. **Дефекты на точках группы B** (`weld_point.important = 'B'`, колонка AG) — **жирно,
   очень заметно**, «требует немедленного вмешательства», идут **первыми**.
2. **Серийные дефекты** — заметная метка «серийный», идут **вторыми**.
3. Остальные — по дате/этапу.

---

## 6. Фото

- Любой участник на своём этапе может прикрепить **фото** дефекта (и ОТК при регистрации).
  Несколько фото на дефект.
- Хранение: файлы в `data/uploads/defects/`, путь в БД (`defect_photo`). Отдача —
  только вошедшим (не публично).

---

## 7. Аналитика (дополнения)

- **Среднее время этапа по отделам** (из таймстемпов) → далее производительность.
- **Возвраты (bounce):** сколько дефектов вернули, кому, отделу-виновнику.
- **Серийные дефекты:** количество, по точкам/группам, динамика.

---

## 8. Права (RBAC) — меняется

- **Админ = WeldTeam.** Админ раздаёт права отделам/пользователям **вручную** и
  **может передавать админские права** другому пользователю.
- **ОТК** — регистрирует дефекты (+ фото).
- **Переоткрытие/переназначение — только WeldTeam** (аварийный клапан).
- **Производство, WeldTeam, ИТО** — запись в Дефекты, но сервер разрешает действие
  **только когда дефект на их этапе** (проверка владения этапом).
- **ОТО** — исполнитель по оборудованию: действует, когда дефект **передан ему**
  (не фиксированный этап цепочки, а заявка от любого отдела). Вне заявок — просмотр.

> Ручная раздача прав и передача админки — отдельный блок (в /users админом). В Фазе 1
> делаем проверку владения этапом и WeldTeam=админ/переоткрытие; UI раздачи прав — позже.

## 9. Модель данных (эскиз)

- `defects` (+поля): `current_stage_dept`, `stage_index`, `status`
  (`registered`/`in_review`/`at_oto`/`unresolved`/`closed`), `delegated_from_dept`
  (куда вернуть после ОТО), `is_serial`, `return_count`, `priority` (вычисляемый),
  ссылки на точку/код как сейчас.
- `defect_stage` — история этапов: `defect_id`, `dept`, `entered_at`, `left_at`,
  `cause`, `countermeasure`, `outcome` (closed / passed / returned), `actor_id`.
- `defect_occurrence` — появления (фиксации): `defect_id`, `date`, `registered_by`
  (для серийных — несколько на дефект).
- `defect_photo` — `defect_id`, `path`, `uploaded_by`, `stage`, `ts`.
- `defect_route` — конфиг маршрута: `code` (или `*`), `position`, `dept` (редактируется).
- `defect_config` — параметры (окно серийности в днях) (редактируется).

Легаси 26 закрытых дефектов остаются как есть (совместимый показ).

## 10. План по фазам

- **Фаза 1 — Бэкенд:** миграция (таблицы выше), движок маршрута (взять/закрыть/передать/
  вернуть), серийность (группы + окно + переоткрытие к закрывшему), таймстемпы,
  RBAC-проверка этапа, легаси-совместимость, тесты.
- **Фаза 2 — UI дефектов:** «Входящие моего отдела» + «Все дефекты», карточка дефекта
  с этапами/4M, действия, жирные точки B + приоритет, метка «серийный», фото (загрузка/
  просмотр). Лёгкий, адаптивный интерфейс.
- **Фаза 3 — Редактор:** редактируемые маршруты (`defect_route`) и окно серийности
  (`defect_config`) как документы.
- **Фаза 4 — Аналитика:** время этапов по отделам, возвраты, серийные (+ база под
  производительность).
