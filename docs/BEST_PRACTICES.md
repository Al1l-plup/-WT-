# Best Practices и тестирование — WeldTeam MES

Рабочее руководство: как вести разработку и проводить тестирование в этом проекте.
Любое изменение должно соответствовать этим правилам. Документ живой — дополняйте по мере роста проекта.

> TL;DR перед коммитом: `ruff check .` → `pytest` → осмысленный коммит в ветку `feature/*` → PR в `DEV`.

---

## 1. Принципы

- **Читаемость важнее краткости.** Новый код пишем в стиле окружающего кода.
- **Одна ответственность на модуль/функцию.** Роуты — тонкие, логика — в helper-модулях.
- **Не ломать историю.** Факты (ТО, дефекты) неизменяемы: контекст замораживается в `snap_*` при записи.
- **Каждое изменение проверяемо.** Если поменяли поведение — есть тест, который это доказывает.
- **Секретов в git нет. Данных пользователей в логах/ответах об ошибках нет.**

## 2. Структура кода

```
app/
├── __init__.py       # create_app() — фабрика, регистрация blueprints, миграции
├── config.py         # конфиг из .env (dev/prod/testing)
├── db.py             # соединение с БД (flask.g)
├── migrations.py     # идемпотентные миграции схемы
├── snapshots.py      # заморозка контекста фактов (историческая целостность)
├── constants.py      # доменные константы
└── blueprints/       # маршруты по разделам (pages, catalog, maintenance, defects, analytics, workers, explorer)
```

Правила:
- Новый набор маршрутов → новый blueprint в `app/blueprints/`, регистрируется в `blueprints/__init__.py`.
- Бизнес-логику, переиспользуемую в нескольких эндпоинтах, выносим в отдельный модуль (`app/snapshots.py` — пример), а не копипастим.
- Ничего не выполнять как side-effect импорта (миграции запускаются из фабрики, не при `import`).

## 3. Стиль и линтинг

- **PEP 8**, проверяется `ruff`. Перед коммитом: `ruff check .` (или `ruff check --fix`).
- Публичные функции — с **docstring** и по возможности **type hints**.
- Осмысленные имена; комментарии объясняют «почему», а не «что».
- Конфиг линтера — в `pyproject.toml`. Исключения (`ignore`) добавляем только осознанно и с комментарием.

## 4. Конфигурация и секреты

- Все настройки — через `.env` (см. `.env.example`). В коде читаем из `app.config`, не хардкодим пути/порты/ключи.
- **`.env` и любые секреты в git не коммитим** (уже в `.gitignore`).
- `SECRET_KEY` для продакшна — обязательно случайный, не дефолтный.

## 5. База данных и миграции

- **Все изменения схемы — только через `app/migrations.py`**, идемпотентным шагом
  (`ALTER ... ADD COLUMN` в try/except или `CREATE TABLE IF NOT EXISTS`). Не править структуру руками в БД.
- Миграция обязана безопасно применяться к уже существующей БД (запускается при каждом старте).
- **SQL всегда параметризованный** (`?`-плейсхолдеры). Не склеивать пользовательский ввод в строку запроса.
- **Миграции — через Alembic** (`migrations/`). Изменил схему → `alembic revision -m "…"`,
  описал шаги в файле версии. Приложение при старте делает `alembic upgrade head`.
- **БД не хранится в git.** Схема — в миграциях, справочники — в `db/seed.sql`
  (пересобрать: `python scripts/dump_seed.py`). Собрать БД: `python scripts/init_db.py`.
- **Историческая целостность:** при записи факта (ТО/дефект) замораживаем контекст в `snap_*`
  (`app/snapshots.py`); чтение/аналитика — из `snap_*` с `COALESCE`-fallback. Правки справочников
  не должны менять прошлые записи.
- **Перед деструктивной операцией с данными — бэкап** (`scripts/reset_facts.py` делает копию в `data/backups/`).

**✅ Закрыто:** Alembic-миграции внедрены; боевая БД вынесена из git (schema+seed); temp-таблицы убраны миграцией.

## 6. Обработка ошибок и логирование

- **Не возвращать `str(e)` клиенту** — это утечка внутренних деталей. Клиенту — обобщённое сообщение,
  подробности — в лог (`app.logger`).
- Не глушить ошибки «немым» `except: pass`. Если ловим — логируем причину.
- Ловить конкретные исключения там, где это возможно (`sqlite3.IntegrityError`, `ValueError`), а не всё подряд.
- Готовый helper: `app/errors.py::api_error(exc)` — логирует и отдаёт безопасный ответ. Используйте его
  в `except`-ветках вместо возврата `str(e)`.

**✅ Закрыто:** все 23 возврата `str(e)` заменены на `api_error`; настроено логирование; добавлен
глобальный обработчик непойманных исключений.

## 7. Безопасность

- Валидация и приведение типов входных данных на границе (уже частично: `int(...)`, `.strip()`).
- Параметризованные запросы (см. §5).
- **Аутентификация/авторизация — планово:** сейчас MES открыт всем в сети. Для продакшна добавить вход
  и разграничение прав (минимум — на запись).

## 8. Git-workflow

- Ветки: `main`/`PROD` — релизные (прямые коммиты запрещены), **`DEV` — рабочая**, `feature/*` и `fix/*` — от `DEV`.
- **Conventional Commits**: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`, `build:`.
- Коммиты — небольшие и логически цельные; репозиторий должен быть работоспособен на каждом коммите.
- В `DEV` — только через Pull Request после ревью. Подробности — в `CONTRIBUTING.md`.
- Не коммитим: `.venv/`, `.env`, `__pycache__/`, `data/backups/`, служебные файлы SQLite.

## 9. Тестирование (обязательная процедура)

### Типы тестов
- **Smoke** (`tests/test_smoke.py`) — ключевые эндпоинты отвечают 200 и возвращают ожидаемую форму.
- **Регрессионные/инвариантные** (`tests/test_history_immutability.py`) — фиксируют гарантии
  (например: после правок справочника историческая карточка не меняется). При добавлении фичи,
  которая что-то гарантирует, — добавляем тест на эту гарантию.
- **Unit** — для чистой логики (валидация, расчёты) без БД.

### Правила
- Тесты работают с **копией БД во временной папке** (фикстура в `tests/conftest.py`) — боевая база не изменяется.
- Каждая новая фича/багфикс сопровождается тестом (для бага — сначала падающий тест, потом фикс).
- Не полагаться на наличие конкретных данных: тест берёт/создаёт нужные данные сам.

### Как запускать
```bash
pip install -r requirements-dev.txt   # один раз
pytest                                 # все тесты
pytest -q tests/test_history_immutability.py   # конкретный файл
ruff check app tests                   # линт
```

## 9a. Фронтенд: мобильные и доступность

Сайт **один** (отдельной мобильной версии нет) — те же страницы открываются с телефона
в цеху. Правила, обязательные для любой новой страницы/компонента:

- **Мета-теги**: `<html lang="ru">`, `charset`, `viewport` (`width=device-width, initial-scale=1.0`),
  `theme-color`. Масштабирование пальцами **не запрещаем** (`user-scalable=no`/`maximum-scale`
  запрещены — WCAG 1.4.4).
- **Поля ввода на мобильном — `font-size: 16px`**. При меньшем размере iOS Safari
  зумит страницу при фокусе. Правило должно покрывать **все** типы (`date`, `email`,
  `password`, `<input>` без `type`), а не только `text`/`number`.
- **Тач-цели ≥ 44px** (Apple HIG 44pt, WCAG 2.5.5): кнопки, ссылки навигации,
  переключатели. В цеху нажимают пальцем, часто в перчатке.
- **Таблицы** — класс `tbl-mobile` + `data-label` у каждой `td`: на узком экране
  строка превращается в карточку с подписями полей вместо горизонтальной каши.
- **Безопасные зоны**: `env(safe-area-inset-*)` в шапке и нижнем отступе страницы
  (вырез и домашняя полоса iPhone).
- **Доступность**: видимый `:focus-visible` (WCAG 2.4.7), `aria-label` у иконочных
  кнопок, поддержка `prefers-reduced-motion` (WCAG 2.3.3), `color-scheme` для нативных
  контролов.
- Регресс ловится тестами `tests/test_mobile_a11y.py` — они проверяют мета-теги на
  **каждом** шаблоне и ключевые CSS-правила. Добавили страницу — тест сам её подхватит.

Проверка живьём: preview на 375px + замер тач-целей/шрифтов полей, затем **обязательно**
контрольный прогон на 1280px — правки мобильных стилей не должны менять десктоп.

## 10. Чек-лист перед коммитом/пушем

- [ ] `ruff check .` — без ошибок (в новом коде; унаследованные предупреждения — отдельно).
- [ ] `pytest` — все зелёные.
- [ ] Новая логика покрыта тестом; изменённое поведение подтверждено тестом.
- [ ] Нет секретов/`.env`/временных файлов в staged.
- [ ] Изменения схемы — новой Alembic-ревизией (`alembic revision`), не правкой БД руками.
- [ ] Ошибки не возвращают внутренние детали клиенту (`api_error`).
- [ ] Изменил справочные данные → пересобрал `db/seed.sql` (`python scripts/dump_seed.py`).
- [ ] Осмысленный commit-message (Conventional Commits); ветка `feature/*`/`fix/*` от `DEV`.
- [ ] Для деструктивных операций с данными — сделан бэкап.
- [ ] Новая страница → есть `viewport`/`theme-color`/`lang`, поля 16px, тач-цели ≥44px (§9a).

- ✅ **CI (GitHub Actions)** — `ruff` + `pytest` на push/PR (`.github/workflows/ci.yml`).
- ✅ **Alembic** для миграций (§5).
- ✅ **Логирование** + отказ от `str(e)` в ответах (§6, `app/errors.py`).
- **Аутентификация** (§7) — следующий крупный этап (поля `email`/`password` в `worker` уже есть).
- **Покрытие** тестами до значимых сценариев записи/закрытия дефектов и планирования ТО.
- **Техдолг фронтенда:** нет базового Jinja-шаблона — `<head>`, шапка и подключение
  скриптов продублированы в 10 файлах (`app/templates/*.html`). Из-за этого мета-теги
  приходится добавлять во все файлы разом (сейчас от рассинхрона страхует
  `tests/test_mobile_a11y.py`). Правильное решение — `base.html` + `{% extends %}`;
  отдельная задача, т.к. затрагивает все страницы.
- (Опционально) полный SCD2-версионинг карточек gun/spot/station — если понадобится видеть старые карточки целиком.
