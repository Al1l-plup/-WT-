# Как вести разработку WeldTeam MES

Правила, по которым проект живёт. Как запустить его у себя — в [README.md](README.md),
принципы кода и тестирования подробно — в [docs/BEST_PRACTICES.md](docs/BEST_PRACTICES.md).

## Ветки

| Ветка | Назначение |
|-------|------------|
| `PROD` | **Боевая.** Ровно то, что работает на сервере цеха (`deploy/update.ps1` берёт её). Прямых коммитов нет — только вливание из `DEV` (выпуск) или срочное исправление через Pull Request. |
| `DEV` | **Разработка и проверка.** Сюда вливаются задачи; здесь их проверяют перед выпуском. На сервер сама не попадает. |
| `feature/…`, `fix/…` | Ветка под задачу, создаётся **от `DEV`**, вливается в `DEV` через Pull Request. |
| `hotfix/…` | Срочное исправление того, что сломалось в цеху: от `PROD`, Pull Request в `PROD`, затем `PROD` вливается в `DEV`. |

```
feature/… ──PR──▶ DEV ──(проверено)──PR──▶ PROD ──▶ сервер цеха (update.ps1)
                   ▲                         │
                   └──── вливание после hotfix ┘
```

## Кто что делает и слова-команды

Работаем с ИИ-помощниками; команды им — одни и те же слова у всех:

| Команда | Владелец репозитория | Остальные разработчики |
|---------|----------------------|------------------------|
| **«пуш»** | Проверки → коммит → push в `DEV`. Сервер не меняется. | Проверки → коммит → push в **свою ветку** → открыть или обновить Pull Request в `DEV`. Сервер не меняется. |
| **«в прод»** | Выпуск: `DEV` → `PROD`, затем `update.ps1` на сервере. | Не выполняется — выпуск в цех делает только владелец. |

«Проверки» — это `ruff check .`, `pytest` и, если изменения видны на сайте или есть миграция,
проверка на копии базы (см. «Перед push»). Pull Request второго разработчика в `DEV` владелец
смотрит и вливает; в `PROD` уходит только то, что уже проверено в `DEV`.

## Задача

```bash
git checkout DEV && git pull origin DEV
git checkout -b feature/kratko-o-zadache      # или fix/…

# работа: небольшие осмысленные коммиты
ruff check . && pytest                         # перед каждым push

git push -u origin feature/kratko-o-zadache
```

Затем — **Pull Request в `DEV`** на GitHub. CI сам прогонит ruff и тесты; второй разработчик
смотрит изменения и вливает. Архивы и файлы, загруженные через сайт GitHub прямо в ветку, —
не способ передать работу: только ветка и Pull Request.

## Выпуск в цех (`DEV` → `PROD`) — только владелец репозитория

1. В `DEV` всё проверено: CI зелёный, изменения посмотрены вживую на копии базы (см. ниже).
2. **Pull Request `DEV` → `PROD`** (или `git push origin DEV:PROD`, если в `PROD` нет ничего,
   чего нет в `DEV`). В описании — что выходит и есть ли миграции, меняющие данные.
3. На сервере (PowerShell от администратора): `powershell -ExecutionPolicy Bypass -File C:\WeldTeam\deploy\update.ps1`.
   Миграции применятся при перезапуске службы.

## Срочное исправление (`hotfix`)

```bash
git checkout PROD && git pull origin PROD
git checkout -b hotfix/kratko
# исправление + тест, ruff, pytest
git push -u origin hotfix/kratko               # Pull Request в PROD → update.ps1 на сервере
git checkout DEV && git pull origin DEV && git merge origin/PROD && git push origin DEV
```

Последний шаг обязателен: иначе следующий выпуск из `DEV` вернёт ошибку обратно.

## Сообщения коммитов

По-русски, в форме `Раздел: что изменилось`, например
`Дефекты: отчёт контролёра за день по выявлениям`. В теле — **зачем** это сделано и что
важно знать: новая миграция и меняет ли она данные, что нужно сделать на сервере
(например, загрузить картинки через сайт).

## Перед push — обязательно

1. `ruff check .` — чисто.
2. `pytest` — всё проходит. Новое поведение — новый тест (тесты сами собирают базу, рабочая не нужна).
3. Изменения видны на сайте — проверить **вживую на копии базы**: `python scripts/qa_server.py`
   (поднимает сайт на копии во временной папке; в логе строка `QA-SANDBOX DB:`), в конце —
   `python scripts/qa_server.py --clean`. С рабочей базой эксперименты не проводим.
4. Есть миграция — прогнать её на копии рабочей базы: `upgrade` → `downgrade` → снова `upgrade`,
   старые данные не должны измениться, откат — чистым.

## База данных и миграции

- Схему меняем **только миграцией**: новый файл в `migrations/versions/` со следующим номером
  (`0032_кратко.py`). Руками структуру базы не правим.
- Миграция **идемпотентна** (`IF NOT EXISTS`, `INSERT OR IGNORE`, проверка колонки перед
  `ADD COLUMN`) и умеет **откатываться** (`downgrade`).
- Данные, которые нужны миграции (каталоги, соответствия), — в `migrations/data/`, не в коде.
- Миграция, меняющая уже записанные данные, подписывает свои правки в журнале
  (`change_log`: `author='миграция NNNN'`) — как `0027` или `0031`. Справочные данные нового
  раздела в журнал не пишем (триггеры аудита на время заливки снимаются — как в `0029`).
- **Ушедшую на сервер миграцию не переписываем** — исправление идёт следующей миграцией.
- Миграции применяются сами при старте приложения — на сервере достаточно `update.ps1`
  после выпуска в `PROD`.

## Данные

- **Сырые данные не меняем никогда.** Что ввели или импортировали — хранится как есть; логика
  работает по рабочим ключам, которые даёт одна функция разбора входа (`app/normalize.py`,
  `app/studs.py` и т. п.).
- **Репозиторий публичный.** В git не кладём: базу, `.env`, фото и загрузки (`data/`), чертежи
  OEM и снимки с водяными знаками, персональные данные. Всё это уже в `.gitignore` — не обходите его.
- Секреты — только в `.env` на сервере.

## Фронтенд

- Без сборки: шаблоны Jinja2 + чистый JS/CSS. Сторонняя библиотека — в `app/static/vendor/`
  вместе с лицензией.
- Поменяли статический файл — поднимите версию в подключении (`studs.js?v=12` → `?v=13`),
  иначе телефоны возьмут старый из кэша.
- Сайт открывают с телефонов: поля ввода от 16px, кнопки от 44px, страница не должна
  уезжать вбок. Фильтры страниц переживают переход между разделами — `static/page-state.js`.

## Скрипты сервера (`deploy/*.ps1`)

Только ASCII и сообщения на английском — кириллица в консоли сервера превращается в
нечитаемые символы. Скрипты должны быть безопасны при повторном запуске и не трогать базу.

## Доступ и защита веток

- Доступ на запись даёт владелец репозитория (Settings → Collaborators). У каждого, кто пушит,
  включена двухфакторная защита входа на GitHub.
- На GitHub (Settings → Rules → Rulesets) ветка **`PROD`** защищена: только через Pull Request,
  вливание — после зелёной проверки CI, без force push и удаления. **`DEV`** — без force push и
  удаления. Ветка по умолчанию — `DEV` (туда по умолчанию открываются Pull Request'ы).
