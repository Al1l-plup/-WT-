# WeldTeam MES

Система цеха точечной сварки кузовного цеха (Body Shop): от эталона точек сварки до
дефектов на конкретной машине. Работает на Windows-сервере в локальной сети цеха,
открывается с компьютеров и телефонов по Wi-Fi — без установки приложений.

Главная идея: **Weld Balance — эталон** (какая точка, какими клещами, на какой станции),
а всё остальное — ТО, дефекты, аналитика, сверка — опирается на него и связывается само.

## Разделы сайта

| Раздел | Адрес | Зачем |
|--------|-------|-------|
| Главная | `/` | Сводка и вход в разделы |
| ТО | `/maintenance` | Обслуживание сварочных клещей: план, записи, проверка тока и усилия |
| Дефекты | `/defects` | Дефекты точек по 4M: регистрация УЗК → цепочка отделов → закрытие с согласованием |
| Шпильки | `/studs` | Недостающие шпильки в сборке: QR карты машины → шпилька на схеме → фото; разбор ИТО/УЗК |
| Шпильки → Визуализация | `/studs/map` | 3D-карта дефектов шпилек по Excel-реестру цеха (схемы и данные — только на сервере) |
| Аналитика | `/analytics` | Дефекты по кодам, станциям, моделям и периодам |
| Сотрудники | `/workers` | Справочник сотрудников |
| Обзор | `/explorer` | Карточки клещей, станций и точек со всеми связями и историей |
| Редактор | `/admin` | Документы цеха в виде таблиц, как в Excel: вставка из Excel, пакетное сохранение |
| Журнал | `/history` | Все правки данных с автором и временем; откат правки, пакета или к точке восстановления |
| Сверка | `/reconciliation` | Расхождения рабочих данных с Weld Balance — разбирает ИТО |
| Пользователи | `/users` | Учётные записи и отделы (только администратор) |

Кто что видит и где может что-то менять — решает отдел сотрудника; правила в одном месте:
[`app/permissions.py`](app/permissions.py).

## Стек

- **Python 3.12** (на нём же идут проверки CI), **Flask**, шаблоны Jinja2
- **Waitress** — сервер для работы в цехе (Windows), **NSSM** — служба Windows с автозапуском
- **SQLite** + **Alembic** (миграции схемы применяются сами при старте приложения)
- Фронтенд — серверные шаблоны и чистый JS/CSS, без сборки; телефон — тот же сайт
- Версии библиотек — [`requirements.txt`](requirements.txt), для разработки — [`requirements-dev.txt`](requirements-dev.txt)

## Устройство проекта

```
app/                 приложение (create_app в __init__.py)
  blueprints/        маршруты: один файл — один раздел сайта (страница + её API)
  templates/         страницы (Jinja2)
  static/            JS/CSS; vendor/ — сторонние библиотеки с лицензиями
  *.py               логика разделов: defect_flow (маршрут дефектов 4M), wb_source и normalize
                     (Weld Balance и рабочие ключи), studs (шпильки), audit (журнал правок и откат),
                     permissions (права отделов), config (настройки из .env) и др.
migrations/          Alembic: versions/ — ревизии схемы, data/ — данные для миграций
db/                  seed.sql — справочники для новой базы, schema.sql — схема для чтения
scripts/             init_db (собрать базу), qa_server (сайт на копии базы), импорты из Excel
deploy/              install.ps1 / update.ps1 — установка и обновление на сервере цеха
tests/               pytest; тесты сами собирают базу из миграций — рабочая база не нужна
docs/                документация (см. ниже)
```

## Запуск у себя

```bash
git clone -b DEV https://github.com/Al1l-plup/-WT-.git
cd -WT-
python -m venv .venv
.venv\Scripts\activate            # Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt
copy .env.example .env            # Linux/macOS: cp .env.example .env
python scripts/init_db.py         # база из миграций + справочники (без рабочих записей)
python run.py                     # разработка; python wsgi.py — как на сервере
```

Сайт: <http://127.0.0.1:5000>. Вход обязателен: зарегистрируйтесь; почта из `ADMIN_EMAIL`
(в `.env`) получает права администратора.

Чтобы проверить изменения на **копии рабочей базы**, а не на ней самой:
`python scripts/qa_server.py` (копия — во временной папке, удаляется `--clean`).

## Сервер цеха

Сервер работает на ветке **`PROD`**. Разработка и проверка идут в **`DEV`**; в цех изменения
попадают только после вливания `DEV` → `PROD` (порядок — в [CONTRIBUTING.md](CONTRIBUTING.md)).

- **Установка и восстановление** (новый сервер или Windows «снесла» Python/Git/службу) —
  PowerShell от администратора: `powershell -ExecutionPolicy Bypass -File C:\WeldTeam\deploy\install.ps1`.
  Ставит Python и Git, окружение, службу `WeldTeamMES`, открывает порт; базу и `.env` не трогает.
- **Обновление** после выпуска в `PROD`:
  `powershell -ExecutionPolicy Bypass -File C:\WeldTeam\deploy\update.ps1` (тоже от администратора).
  Миграции базы применяются при перезапуске службы.
- Порт и прочие настройки — в `C:\WeldTeam\.env`; лог — `C:\WeldTeam\logs\server.log`.

Скрипты в `deploy/` — источник правды по установке; ручная пошаговая инструкция —
[`docs/DEPLOY_WINDOWS.md`](docs/DEPLOY_WINDOWS.md) (версии в ней могут отставать от скриптов).

## Данные — главные правила

- **База в git не хранится** (`data/` в `.gitignore`). Схема меняется только миграциями,
  справочники для новой базы — `db/seed.sql`.
- **Фото, схемы и чертежи** (`data/uploads/`) в git не хранятся: **репозиторий публичный**,
  чертежи OEM и снимки с водяными знаками загружаются на сервер через сайт.
- **Сырые данные не меняем**: что ввели или импортировали — хранится как есть, логика
  работает по рабочим ключам из одной функции разбора входа.
- **Каждая правка — в журнале** (`change_log`, триггеры строит `app/audit.py`) и откатывается.
- **Факт помнит свой день**: дефект хранит снимок станции и модели на момент регистрации
  (`app/snapshots.py`), поэтому сегодняшние правки эталона не переписывают историю.

## Настройки

Читаются из `.env` (пример — [`.env.example`](.env.example), значения по умолчанию и полный
список — [`app/config.py`](app/config.py)). Главное: `SECRET_KEY`, `HOST`, `PORT`, `ADMIN_EMAIL`;
Telegram-уведомления включаются только при заданном токене бота.
